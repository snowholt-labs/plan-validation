# Changelog

## Unreleased

- Add report format version 4 for new reports: a light blue, tabbed page with a header card, a score strip and the tabs Summary, Needs your answer, Watch list and Full report. The Summary shows 1–3 diagrams of the planned design, drawn as inline SVG from `context.json` data, with every label checked to fit and nothing overlapping; counts of pending decisions and watch-list items; and the next session's first prompt. New `context.json` fields: `project`, `audience`, `title_accent`, `diagrams`, `open_decisions` and `watch_list`; `feature` is dropped. Without JavaScript every tab shows in order, and print shows everything. The page stays self-contained under the same strict content security policy. Saved version 1–3 reports render exactly as before. The demo report uses version 4.
- Every new report now says whether to run validation again: yes, no or stop, with one to four reasons and "Run <n> of at most 3". The renderer requires yes or stop when the confidence is below 70% or Unknown, a revised average is below 8.0 or Unknown, or the verdict is Not ready, and never allows yes at run 3. A yes includes a copyable re-run prompt of at most 80 words, saved as `rerun.txt`, that keeps a phase-only run's scope, runs before any phase starts (in a Not ready report, after the remediation session), and never starts implementation. Until that run, a current Ready or Ready after approvals report with a ready phase shows "Run validation again first" on its phase prompts instead of a copy button, drops the Prompt .txt link and puts the re-run card above the next session; `handoff.txt` and the phase prompt files then start with a held note, and the renderer's JSON output says `handoff_held`. In a new report, section 8 must carry the run-first line exactly when the answer is yes and a phase is ready, even after the handoff turns historical. A new report's re-run prompt must start with the validate-plan invocation and name the plan, the spec and this run's `report.md` as the previous report. Runs are counted per repository-relative plan path and scope through the new `validation_run` field; re-renders do not count, and a fourth run needs the user's explicit reset. When the plan or spec changes after review, the historical warning names the next run (a saved re-render names none) instead of more review rounds; at run 3 it says the run limit is reached, so revalidating the same scope needs the user's explicit reset, and after a recorded stop it says to decide the next step first. The demo report recommends running validation again.
- For every report version, the renderer rejects a malformed `documents` field (not a list of PLAN and SPEC objects with string `label`, `path` and `sha256`, or a path that is not a valid file name) with a message naming the problem instead of a Python traceback.
- In a version 4 report with a Ready after approvals verdict, each pending decision that holds back work must be named in the `waits_for` of a waiting phase.
- A version 4 remediation prompt, like the re-run prompt, may not contain `implements`, `implementing`, `reimplement` or `re-implement` either, unless right after a negation, and the renderer now names the word it rejected. A backtick-quoted slash command such as `/feature-dev:implement`, `/implement/` or `/implement /repo/plan.md` no longer counts as a path, so it cannot hide the word, and its words count toward the 80-word limit; a quoted path with spaces is checked like other text. Version 4 phase prompts also treat `cannot` and a curly apostrophe (`don’t`) as negations of the stop and merge sentences.
- In Claude Code, add an off-by-default plugin setting, `publish_artifact`, that publishes each new report to your claude.ai account as a private artifact and gives its link before the local one. The skill never shares the artifact, pins it or changes its visibility, and makes no publish call while the setting is off, in Codex or in a standalone skill install. A failed publish falls back to the local report.
- For repositories that review docs PRs, the "Phased implementation" page recommends a review rule for a docs PR of a validated spec and plan: review fixes only local defects, sends design gaps back to validation (counted toward the 3-run limit) and allows at most 3 code review rounds on the PR.
- The documentation website asks for consent before it loads Google Analytics. Nothing third-party loads until a visitor accepts. Declining, or changing the choice later through **Cookie settings** in the footer, removes the analytics cookies and reloads a page where analytics was running. The choice is asked again after a year. The plugin and its reports are unchanged and send nothing to Google.

## 0.4.0 — 2026-10-25

- Add an opt-in `--open` flag to the report renderer that asks Python's `webbrowser` module to open `report.html` in a graphical browser. New reports are rendered with it; a re-render opens the browser only when the user asked to see the report again. Opening is best effort and never stops the report from being written; the agent's reply always keeps the `report.html` link.
- Reject a new report whose later phase prompt does not say `Confirm Phase <previous> is merged`, and stop treating a split plan phase as one PR, so a plan run in several sessions cannot end each session without a merge. The skill follows repository branch conventions first, then the user's, and raises a one-PR delivery across phases as an approval when neither defines per-phase delivery.
- Add a pre-mortem to `revise-prompt`. It names the prompt type, scores five anchored dimensions, and replaces the weakness list and the critique's risk line with one table of up to five likely failures, each with its cause, impact and fix; the overall risk is stated once, with the revision. Only blocking questions wait, at most four per batch (down from five) to fit Claude Code's question tool; optional questions are asked only alongside a blocking one, and otherwise become recorded defaults the user can change. A failed run's output starts a post-mortem with a minimal fix. Revisions trace every added line to a listed failure, a user answer, a recorded default or a guard against a High-impact failure, list their changes, confirm that nothing was lost and suggest a test the user runs. The skill no longer opens secret files or checks credentials, even to judge feasibility, does not repeat a secret found in a prompt or run output, and accepts only revision preferences, never permissions, as instructions to itself. `SECURITY.md` no longer says the skill waits for explicit defaults.

## 0.3.0 — 2026-10-20

- Group a validated plan's tasks into small phases and give one launch prompt per ready phase, so each phase runs in its own fresh session and stops at the phase end. Phases keep plan order and plan phase boundaries, target 3–5 tasks, and flag docs-only phases and phases that need a security review.
- Add report format version 3 for new reports: a validated task inventory and phase list, one prompt of at most 80 words per ready phase with a checked `Stop at the end of Phase <id>` sentence, `handoff-phase-<id>.txt` files, a phase table and one copy button per phase prompt. Not ready reports, and reports whose first phase waits for an approval, keep one remediation prompt.
- After earlier phases merge, validate the remaining phases as a phase-only validation instead of re-rendering the old report. Historical phase tables show "Revalidate before starting".
- Add a "Phased implementation" documentation page with the recommended per-phase workflow: one fresh session per phase after the previous phase merges, a severity-based review loop, a security review only for flagged phases, and full code and security review on the plan-to-main PR. The repository's own `AGENTS.md` adopts this workflow, and the evaluation cases cover phase grouping, waiting phases and between-phase changes.
- Relicense the project from MIT to the Apache License 2.0 and add a NOTICE file that credits the original project and its creator. Versions up to 0.2.0 remain available under the MIT License.
- Add plugin icons: light, dark and composer icons for Codex, and a directory icon for Anthropic's plugin directory. Generated HTML reports show an inline favicon.
- Shorten new fresh-session handoffs to a 50–80-word target, with explicit phase/validated-plan scope and links to the complete evidence and permission record.
- Add a local, accessible “Feature at a glance” block diagram, plain-language summaries and expandable technical evidence. Keep both complete score tables, blockers and required approvals visible.
- Use and disclose recommended defaults for unanswered routine clarifications, including prompt revision; keep required facts and approvals pending.
- Run public research by default instead of asking before each lookup; host permission settings still apply. Queries stay public-only, every lookup is listed in the report, and users can decline research for a run.
- Stop asking routine questions during validation. Apply the recommended best practice and disclose it; record choices that need approval as a menu with a recommendation in the report, without pausing independent work.
- Tell the implementing agent to continue through passing steps and reviews without asking to continue, stopping only for a required approval, an unfixable failure or the scope end.
- Suggest a reasoning effort for the validation and next sessions; never set or require one.
- Report format version 2 (the "Feature at a glance" diagram and "Decisions made without your reply") was added during this release's development and is superseded by version 3, which keeps both. The renderer still reads saved version 1 and 2 reports. Existing reports and planning documents are not migrated.

## 0.2.0 — 2026-10-14

- Add focused review of proposed/changed dependencies and relevant existing security-critical components, with dated primary evidence and High/Medium/Low decision confidence.
- Compare the original approach with at most two suitable alternatives, including the existing implementation or no dependency; verify plugin ownership, availability and fit.
- Require approval before each external lookup, including web and Context7; exclude confidential queries and continue independent checks when permission/access is unavailable.
- Preserve installation/execution/service boundaries, inspect planned commands before rehearsal, and record actionable decisions in the report and handoff.
- Add portable `revise-prompt`: critique, score, clarify, wait for complete answers or explicit defaults, then produce a copy-ready revision without executing the prompt. The personal source skill remains unchanged.
- Preserve the eight-section HTML contract, both PLAN/SPEC score tables, scope changes and full handoff; add dependency comparison and no-concern renderer regressions.
- Update manifests, documentation, privacy disclosures, examples and wiki. No runtime dependencies or telemetry added.

Verification evidence and limitations are recorded in [docs/verification.md](docs/verification.md). Directory scanning, reviewer approval and live listing remain separate from GitHub release publication.

## 0.1.0 — 2026-10-14

Initial public pilot.

- Bundle `validate-plan` and `validation-args` as a Claude Code plugin and installable Codex skills.
- Preserve the existing HTML renderer, report assets and regression tests.
- Adapt private host-specific instructions into a shared workflow with explicit invocation, repository-defined permissions and no mandatory external planning plugin.
- Include a local reviewer brief, evidence/report contract and permission-preserving implementation handoff.
- Document installation, first use, updates, removal, privacy and verification limits.
- Add a deterministic demonstration, package checks and CI.

The release does not establish end-to-end agent reliability, cross-platform behavior or comparative time/cost improvements.
