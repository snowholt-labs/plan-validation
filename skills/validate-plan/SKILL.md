# Validate an implementation plan

Review the plan against the approved specification and current repository, rehearse its implementation where authorized, and preserve what actually happened. This is a validation workflow, not delivery of the feature.

## Host and inputs

- Codex standalone skills: `$validate-plan`; `$validation-args` prepares the inputs.
- Claude Code plugin: `/plan-validation:validate-plan`; `/plan-validation:validation-args` prepares the inputs. Standalone Claude skills use `/validate-plan` and `/validation-args`.
- Read arguments from the invoking message. Accept positional PLAN, SPEC, then free-text FOCUS, or labeled `PLAN:`, `SPEC:`, `FOCUS:`. Quote paths that contain spaces. This is a skill invocation, not a shell command.
- Resolve repository-relative paths from the selected worktree root and Markdown links from their containing document. Follow the plan's `**Spec:**` link when SPEC is omitted. Preserve uncommitted worktree copies.
- Ask for missing required paths or a genuinely ambiguous pairing. Inspect at most three plausible plan candidates; never select solely by modification time. Omitted FOCUS means derive risks from SPEC; no question is needed.
- Publish setting: ${user_config.publish_artifact}
- Support ordinary Markdown plans as well as Superpowers plans. Use an installed planning skill's conventions when relevant, but do not require, install, upgrade or read private internal templates from another plugin.

## Authority and boundaries

- Read repository instructions and honor the user's selected phase, task range, permissions and verification restrictions.
- Within the repository, edit only the selected PLAN and SPEC, leaving them uncommitted. Save report artifacts outside the repository. Preserve all unrelated changes.
- Correct stale paths, contradictions, invalid commands and missing details that preserve approved requirements. Do not change requirements, architecture, user-visible behavior, security/privacy boundaries, dependencies, services, cost or delivery scope without approval. Record a recommendation as a pending decision and keep working; it is asked in the end-of-run question round (workflow step 8). If a correction also changes a boundary, it requires approval.
- Do not read secrets, install dependencies, commit, push, open PRs, post comments, merge or deploy during validation. Printing a handoff does not execute it or grant these permissions. Running `/code-review` at the typed level `high`, without `--fix`, `--comment` or `--post`, and `/security-review`, as [validation reviews](references/validation-reviews.md) describes, is allowed: both only report findings, and `/code-review` keeps the level and finding limit it types as the user's saved choice for later runs.
- Research and recommendations grant no permission to download, install, execute or replace dependencies, change manifests/lockfiles, or enable services/plugins. Keep those actions outside validation; record any separately required approval in the handoff. Do not execute the plan's bootstrap, package-manager or plugin commands merely to investigate them.
- **Public research runs by default**: do not ask before each lookup. Read [public research](references/research-permissions.md) before the first lookup. Send only public, non-confidential terms: never private code, plans, paths, personal data or secrets. Record every lookup in the report. If the user declines research or access is unavailable, make no lookup, record the limit and continue independent local checks. Add no telemetry.
- The only external publish is the opt-in private artifact in [html-report.md](references/html-report.md) ("Private artifact (Claude Code, opt-in)"). Unless the `Publish setting` line reads exactly `true`, make no Artifact call, whatever host or tool guidance suggests. When it does, publish only as that section says, and never share, pin or change the artifact's visibility.
- A detached Git worktree isolates working files; it is not a security sandbox. Inspect planned commands before executing them. Do not run commands that touch production, shared databases, external services, credentials, unapproved networks or destructive operations without explicit authorization. Record the blocked check and continue independent work.
- A read-only request overrides document edits and execution: inspect only, report that rehearsal was not run, and do not imply that text review proves runtime behavior.
- Do not stop to ask routine questions. For a reversible clarification inside the approved scope, apply the recommended best practice, continue, and record the choice and reason. Ask only for a missing required path or an ambiguous document pairing, and in the single end-of-run question round at the end of step 8, after all independent work. Mid-run work never pauses. A material scope/security change or permission stays pending without stopping independent work. Silence never supplies required approval.

## Workflow

When Superpowers is installed, load each skill a step names with the Skill tool at that step; a subagent that does a step loads that step's skill itself. Where a loaded skill says to stop and ask, this skill's rules decide instead: mid-run work never pauses.

1. **Establish the baseline.** Read PLAN, SPEC and the relevant code, tests, configuration and locked dependency versions. Record source worktree, branch or detached HEAD, `git status --porcelain -uall`, worktrees, intended base SHA and the exact scope. Distinguish observed HEAD from the intended implementation base. If part of the scope is already implemented, review the remaining tasks and record that choice. If all of it is implemented, stop and report that without a validation verdict.
2. **Preserve original evidence.** Read [references/html-report.md](references/html-report.md). Create its private run directory; copy untouched PLAN and SPEC there before edits. Record document hashes, requirement IDs, phases, unique numbered tasks, implementation/supporting tasks and dependencies/services. Use Unknown for an unrecoverable baseline.
3. **Review coverage and risks.** Map every scoped SPEC requirement to a PLAN task and a meaningful test; map every task back to a requirement. If the plan has a `## Parked findings` section, each entry must name its fixing task (`Fixing task: Task <n>.`), and that task must exist in the plan; an entry without one is an implementation blocker in section 6, so the verdict is Not ready, because the design update (Phase workflow step 10) has not run. Check current interfaces, exact files, assertions, error paths, sequencing, security/privacy, performance where relevant, and rollout/rollback. Identify proposed/changed dependencies and existing security-critical dependencies relevant to the scoped behavior. Do not audit the entire dependency tree indiscriminately. When applicable, read [dependencies and alternatives](references/dependencies-and-alternatives.md) and compare the original approach with at most two strong alternatives, considering the existing implementation or no new dependency. Verify external claims through recorded public lookups. Label findings Verified, Assumption or Unknown and cite dated primary-source evidence. If no concern or consequential alternative applies, record that briefly; do not invent a comparison or a decision menu.
4. **Revise with scope control.** Repair defects inside existing tasks where practical. Require precise interfaces, fixed values, test assertions and commands; do not demand complete routine implementation bodies. Keep existing document structure and decision IDs. Explain every task split/addition/removal and repeated check. Preserve the branch, review and merge conventions that repository instructions define, or the user's where the repository's are silent; do not invent others. One exception: when the plan has no `## Phase workflow` heading, add the block from [phase-workflow.md](references/phase-workflow.md) once, near the top of the plan, and record it in section 5 as a plan change whose approval basis is this skill's Phase workflow rule. The block grants no permission: its review and delivery steps follow the repository's own rules. A read-only request adds nothing. Collect material approval questions; leave affected requirements unchanged until answered.
5. **Rehearse the authorized scope.** Inspect planned commands, wrappers, lifecycle/install scripts, downloads, permissions and external/shared-state effects before running anything. Block only tasks dependent on unresolved safety or permission decisions; continue independent approved checks. Create a new detached worktree at the confirmed implementation base. Use a gitignored `.worktrees/plan-dryrun-<topic>` path or a session temporary directory. Implement enough of each authorized task to exercise its instructions and assertions; skip installation, dependency changes, commit, push, PR and deployment steps. Run only approved focused commands whose dependencies already exist and whose use is authorized; do not execute a suspect dependency to assess its safety. Record exact commands, exit codes, outputs and relevant counts. A blocked environment is a recorded limitation, not a passing check. Before changing the plan for a failing command, find the cause (`superpowers:systematic-debugging` when installed): read the full error, reproduce it, and trace it to the plan, the code or the environment. Repair the plan only when the cause is a plan defect; record an environment cause as a limitation.
6. **Run the independent review loop.** When delegation is available and permitted, dispatch a fresh review agent the way `superpowers:requesting-code-review` does: a new subagent that gets only the brief, never this session's history, and returns only its findings. Always use the [plan-reviewer.md](references/plan-reviewer.md) brief: the documents are uncommitted, so there is no commit range for a diff template. Give it the revised documents and the original scope snapshots. Reviewers are read-only and return findings as their final response; wait for the completed response. Triage each finding against the code and documents (`superpowers:receiving-code-review` behavior): verify it, push back with evidence on a wrong one, and never reword correct text. Fix verified Medium and High findings in the plan or spec, then review again with a fresh agent, until none remain. There is no round cap. After the first round, give each new reviewer the current documents, add the changes since the last round to `Review focus` after the user's focus, and list the earlier findings under `Findings already dispositioned`. If the same finding returns after a fix, or three fixes for one problem fail, stop editing that part and question the approach (`superpowers:systematic-debugging`): record the finding in section 6 as an implementation blocker, so the verdict is Not ready, never in `decisions_without_reply`. The loop continues for the other findings, and the run finishes without pausing. A finding whose fix would change requirements, architecture, security boundaries or scope is not fixed: it becomes a pending approval for the step 8 question round and leaves the loop. List Low findings without fixing them. Record each finding's disposition. If an independent reviewer is unavailable, disclose that gap and use Not ready until a separate review is supplied; never present self-review as independent. Recheck material later edits.
7. **Record decisions; ask them at the end.** Complete independent validation, review and report preparation without pausing for choices. For a routine, in-scope choice, apply the recommended best practice and record the question, choice and reason in `decisions_without_reply`; reflect it in the selected documents where needed so they remain usable. For a choice that needs approval, write a concise menu in section 6: keep the original approach, adopt a named verified alternative (at most two), or defer. Mark the recommendation with reasons, tradeoffs, effort and High/Medium/Low confidence. A blocked option must name its unsatisfied conditions; choosing it does not waive execution approvals. Leave affected requirements unchanged and dependent tasks waiting. Record each pending choice as a question for the step 8 question round; do not stop to ask now. When the user answers, record it in sections 5–6, apply and recheck the affected changes, then re-render the report, context and handoff; an answer that edits PLAN or SPEC first follows step 8's answer-edit steps. For a version 4 report, do not re-render or migrate it; validate the plan again, and the new run uses version 5. Once earlier phases have merged, validate the remaining phases as a phase-only validation instead, as the handoff template describes. Treat the earlier handoff as historical. Do not repeat settled questions or convert defaults into user approvals. Recheck affected sections after an approved change without chasing a perfect score.
8. **Clean up and deliver.** Inspect the exact worktree created by this run, preserve evidence, then remove only that disposable worktree. Force removal is allowed only for its known rehearsal edits; never remove another checkout or unknown work. Compare final branch, status and worktree inventory with the baseline. Report concurrent changes without reverting or switching them. Then run the final code and security reviews once each, as [validation reviews](references/validation-reviews.md) describes. Before scoring, check that every claim in the verdict and section 7 rests on a command or review that ran in this run (`superpowers:verification-before-completion` behavior); relabel or remove any claim that does not. Score and render the complete report below.
   Then ask one round of questions: each pending approval with its recommendation, and the Low review findings to fix or skip. Use AskUserQuestion in Claude Code and ask in chat in Codex. For a `kind: new` version 5 run, handle the answers in this order:

   1. **End-of-run round.** The end-of-run round is the questions this run asked in step 8 and the user's reply to them: in Claude Code the AskUserQuestion results (one call holds at most four questions, so a round can take several calls, and a dismissed or failed call leaves its questions unanswered); in Codex the user's next chat message after the questions. The round ends when the run delivers its final reply after handling that reply. A question the reply does not answer stays pending. Answers given after the round get a local re-render and no hash refresh, and the reply says to validate the revised plan to get current prompts.
   2. **No edit.** If no answer changed PLAN or SPEC, skip items 3–9 and keep the recorded hashes. The artifact and `--open` rules below still apply.
   3. **Hand edits.** Before applying any answer edit, compare the live PLAN and SPEC with `revised-plan.md` and `revised-spec.md` in the run directory; any difference is a hand edit. When they match, write the SHA-256 of both documents to `last-write.json` in the run directory. Before each of the run's own writes to PLAN or SPEC, the live file's hash must equal that record; right after each own write, record the new hash. A failed check means a hand edit: report it in the reply and section 7, apply the remaining answer edits without overwriting the user's change, skip items 5–8, and refresh no hash, so the prompts stay historical and the reply says to validate the revised plan for current prompts.
   4. **Apply.** Apply the edits the answers require in full, with step 7's rechecks of affected sections.
   5. **Rehearse changed tasks.** If an answer changed the commands, files or test assertions of a task that step 5 rehearsed, rehearse only those tasks again under step 5's rules: a new detached worktree at a path this run has not used (not the step 5 path), at the same recorded implementation base SHA; the edits of earlier tasks a changed task builds on applied as setup only, not recorded as new results; approved focused commands only; exact commands, exit codes and outputs recorded; a failing command traced to its cause before the plan changes. Then inspect and remove only that worktree under this step's cleanup rules, and compare the worktree inventory with the baseline again. A changed task that step 5 did not rehearse keeps its recorded step 5 limit, and the verdict follows the existing rules. If the rehearsal cannot run, record the limit in section 7. The changed tasks' phases cannot be Ready, and because a waiting phase under Ready after approvals must name a pending approval and missing required evidence is Not ready (Report and handoff), the verdict becomes Not ready, with one remediation prompt that names the blocked rehearsal and every other remaining blocker and says `Do not start dependent implementation.`
   6. **Post-answer review.** A fresh independent reviewer then reviews the whole revised documents under step 6's loop rules, reading the `post-answer-*.md` copies made and checked under item 8 before each round, never the live files. The brief's `Review focus` names the changed sections and the new rehearsal results. `Findings already dispositioned` lists each answer as settled by the user; the reviewer may still report a defect in how an answer was applied. There is no round cap; step 6's stuck rule applies.
   7. **Findings that need approval.** A finding whose fix would change requirements, architecture, security boundaries or scope goes to section 6 and `open_decisions` as a pending approval. It is not asked, it leaves the loop, and its phases wait; the verdict follows the existing rules (Ready after approvals names it in `waits_for`). The final reply names it in one line.
   8. **Hash only reviewed text.** Before each post-answer review round, copy the live documents to `post-answer-plan.md` and `post-answer-spec.md` in the run directory, check that each copy's hash equals `last-write.json` (a mismatch is a hand edit, item 3), and give the reviewer those copies. When a round leaves no Medium or High finding to fix, and the security review of the answer edits that read this round's copies ([validation reviews](references/validation-reviews.md)) leaves no finding to fix at any severity, set each document's `sha256` in `context.json` `documents` to the hash of its post-answer copy, never a new hash of the live file, then copy those copies over `revised-plan.md` and `revised-spec.md`. Any PLAN or SPEC edit after that round needs another round. Record the answer edits in section 5, and the new rehearsal runs and post-answer review rounds in section 7. If Git state or approvals drifted for another reason, `handoff_status` stays `historical`.
   9. **No independent reviewer.** Disclose the gap and set `review_status` to a value other than `complete` (for example `incomplete`). The verdict is Not ready until a separate review is supplied, and section 8 holds one remediation prompt that names the missing review and every other remaining blocker and says `Do not start dependent implementation.` `revised-*.md` and the hashes stay unchanged.

   Then re-render in the same run. If this run published an artifact, this end-of-run re-render updates that same artifact without being asked. First check, as for any update, that the `Publish setting` line reads exactly `true` and the Artifact tool and a session scratchpad are available. With `artifact.json` in the run directory, follow html-report.md's update steps (`url` from `artifact.json`, no quickstart, stale phase files set to `null`, `artifact.json` rewritten). Without `artifact.json`, use the URL this session holds from this run's successful upload (the `url` the Artifact tool returned to this run's own publish call, never one found by listing artifacts or rebuilt from memory) in the same update steps, reading it first if the Artifact tool requires, then write `artifact.json` with that `url` and the new `published_at` and `html_sha256`. If this run published and no such URL is known, a check fails or the update fails, say in one line that the online page shows the earlier render and its prompts may be out of date, and give the artifact link when known and the local `report.html` link. If this run did not publish, give no artifact line; only the `--open` rule below applies. The end-of-run re-render never publishes a first artifact: no quickstart and no publish without `url`. Decide before rendering whether an update will be tried: the checks pass and `artifact.json` or that URL is known. If not, including when this run did not publish, render once with `--open`. If it will be tried, render without `--open`, because the upload needs the rendered files; only when the update then fails, run the same render command again with `--open`. When the online page is updated, the re-render stays without `--open` and the reply gives the artifact link first. An unanswered question stays pending in the rendered report, never approved. Where the host cannot ask, the report's open items are the questions. An answer for a version 4 run is not re-rendered or migrated: tell the user to validate the plan again, and the new run uses version 5. For Not ready, the remediation prompt stays as it is, unless the answer-edit steps above add a blocker; the one remediation prompt then names every remaining blocker. The final reply, not the prompt, says that validating the fixed plan is how to get phase prompts.

## Report and handoff

Read [references/report-contract.md](references/report-contract.md) for the rubric and eight required sections. Deliver both five-dimension comparison tables and their calculated averages, decision confidence with evidence, scope comparison, actual checks and limits, and the complete handoff. Include applicable dependency/alternative comparisons inside this report. Dependency decisions use High/Medium/Low with reasons and unknowns, never numeric trust scores. Existing document scores and subjective readiness estimates are not security guarantees or calibrated probabilities.

For new reports, use format version 5, which is version 4 without `validation_run` and `rerun` (version 4 renders saved reports only): a Summary tab with 1–3 diagrams of the intended design (not the validation workflow; each diagram's eyebrow says whether it shows planned, existing or changing parts, a node's sub-line can mark a single part that differs, and invent no connections the spec does not describe), `open_decisions` that mirror section 6's pending approvals for the validated scope, and a `watch_list` of gaps, limits, risks and fixed items; then the eight evidence sections with concise summaries and expandable technical details, “Decisions made without your reply” at the end, and the phase grouping below. Keep blockers, pending approvals and both full score tables visible. Target 50–80 words per launch prompt, referencing the plan, spec and saved report; do not duplicate the evidence in it. Existing reports and plans are not migrated or reformatted merely because the plugin changed.

- **Ready:** no material blocker, and no unresolved approval that holds back work in the named implementation scope, with the independent review completed.
- **Ready after approvals:** only identified non-blocking approvals remain, and at least one holds back dependent work in the named scope; that work's phase waits, and a waiting phase names the decision ID in `waits_for`.
- **Not ready:** a blocker remains or required independent review/evidence is missing. Include a remediation prompt stating `Do not start dependent implementation.`

### Phase grouping

Group the validated tasks into implementation phases so that each phase runs in its own fresh session. The grouping lives only in the report and `context.json` (`task_inventory` and `phases`); never add, rename or reorder phase headings or tasks in the plan file for it.

- Put every validated task in exactly one phase, in plan order. Never split or move a task.
- Never cross a phase or part the plan already defines. Split a plan phase larger than about 5 tasks into consecutive sub-phases; keep small plan phases as they are, even with one task. A plan with no phases of its own and 5 or fewer tasks is one phase.
- Each later phase's prompt confirms the previous phase is merged; never weaken that check. A delivery that cannot merge each phase on its own is a plan defect: apply per-phase delivery from repository or user instructions, which are the approval basis; otherwise raise it as an approval in section 6.
- Target 3–5 tasks per phase. End each phase where the tests pass and its PR can be reviewed on its own.
- Record for each phase whether it is docs-only, whether it is security-sensitive and why (auth, user input, secrets, dependencies, CI workflows), and whether it is ready or waits, naming what it waits for. The `security_review` flag marks where review should look hardest; it does not decide whether a security review runs: a code phase on the current Phase workflow gets one at step 9, a code phase on an older block, or with none, gets one when flagged, and a docs-only phase gets the reviews the repository's rules require.
- Write one done-check line per phase in section 8, before the between-phases note and the prompts: `Done-check, Phase <id>: <commands>`, unfenced, because a fenced block counts as a prompt. It lists commands to run later, not results: the phase's task test commands, the integration test that proves a task crossing a boundary, and the full unit and integration suites. Name only tests that exist once the phase is done, never one a later phase adds, and build it from the task test commands that step 5 rehearsed or step 6 reviewed. A missing test or assertion inside a task is an in-task repair (step 4); new test infrastructure, such as a service, container, dependency or CI job, is a pending approval.
- Phases run in order, so a waiting phase holds back every later phase. A phase whose tasks are only partly approved waits as a whole. If the first phase waits, no phase can start: section 8 holds one prompt that names what to resolve and says `Do not start dependent implementation.`
- A phase-only validation groups only the selected scope.

Suggest, never set, a reasoning effort for the next session, as described in the template. Instantiate [handoff-template.md](handoff-template.md) with verified paths: one prompt per ready phase, each naming its phase and tasks, following the plan's Phase workflow and stopping at that phase's end. Keep revisions, checks, decisions and permissions in the referenced report/context. Never add commit, PR, comment, merge, deployment, dependency or service permissions. Repository-specific workflow belongs in repository instructions, not in the universal launch prompt. The recommended per-phase workflow for repositories is published at https://snowholt-labs.github.io/plan-validation/phased-implementation/.

Use `scripts/render_report.py` with the files described in [references/html-report.md](references/html-report.md). Inspect the output, the exact `handoff.txt` and each `handoff-phase-<id>.txt` listed under `phase_handoffs` in the renderer's JSON output. The renderer checks structure, arithmetic and document fingerprints; it does not prove that an agent review or command actually occurred.

Return a brief verdict, a clickable absolute link to `report.html`, the suggested effort for the next session, and any immediate blocker or pending choice. Render a new run's report with `--open`, and say the report was sent to the browser only when the renderer printed `"opened": true`. A re-render after a recorded answer is a re-render, as in Resume or repeat below, except that the step 8 re-render after the end-of-run answers also updates this run's own artifact, and adds `--open` whenever it does not update the online page. For a new run, when the `Publish setting` line above reads exactly `true`, check before rendering that the Artifact tool (a deferred tool that can be loaded counts) and a session scratchpad are available. If they are, render without `--open`, publish the private artifact as html-report.md describes and give its link before the local link. If either is missing, say so in one line and render with `--open`. If publishing fails, follow html-report.md's failure rules: one line, the local link, and the artifact link first when the upload itself succeeded. If routine defaults were used, briefly identify the choices and reasons at the end; the report retains the complete record. The HTML must contain the full report even when chat is concise. If the user asks for the full report in chat, include all eight sections, the Summary diagrams' descriptions, the open decisions, the watch list and defaulted decisions as well.

## Resume or repeat

Keep the original/revised snapshots, hashes, commands/results, reviewer response, tested SHA, scope, approvals, report and handoff in the durable run directory. Read that record after compaction; never reconstruct counts or approvals from a vague recap.

When asked to repeat results, verify current document hashes, worktree, base and approvals, then link the saved complete report. A re-render or repeat is not a new run. Regenerate missing HTML from saved evidence without claiming a new validation; pass `--open` on a re-render only when the user asked to see the report again, except the step 8 end-of-run re-render, which adds `--open` whenever it does not update the online page. When the run directory has `artifact.json`, follow html-report.md for its link; update that artifact, or publish a `kind: saved` report, only when the user asks to publish or update it, except the step 8 re-render after the end-of-run answers, which updates this run's own artifact. Mark changed or unverifiable state historical; retain the historical prompt and provide a current remediation prompt when needed. Do not replace recorded hashes to make stale evidence appear current. The only exception is step 8's post-answer review in the same run. Static HTML only reflects checks made when rendered.
