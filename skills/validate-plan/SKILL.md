# Validate an implementation plan

Review the plan against the approved specification and current repository, rehearse its implementation where authorized, and preserve what actually happened. This is a validation workflow, not delivery of the feature.

## Host and inputs

- Codex standalone skills: `$validate-plan`; `$validation-args` prepares the inputs.
- Claude Code plugin: `/plan-validation:validate-plan`; `/plan-validation:validation-args` prepares the inputs. Standalone Claude skills use `/validate-plan` and `/validation-args`.
- Read arguments from the invoking message. Accept positional PLAN, SPEC, then free-text FOCUS, or labeled `PLAN:`, `SPEC:`, `FOCUS:`. Quote paths that contain spaces. This is a skill invocation, not a shell command.
- Resolve repository-relative paths from the selected worktree root and Markdown links from their containing document. Follow the plan's `**Spec:**` link when SPEC is omitted. Preserve uncommitted worktree copies.
- Ask for missing required paths or a genuinely ambiguous pairing. Inspect at most three plausible plan candidates; never select solely by modification time. Omitted FOCUS means derive risks from SPEC; no question is needed.
- Support ordinary Markdown plans as well as Superpowers plans. Use an installed planning skill's conventions when relevant, but do not require, install, upgrade or read private internal templates from another plugin.

## Authority and boundaries

- Read repository instructions and honor the user's selected phase, task range, permissions and verification restrictions.
- Within the repository, edit only the selected PLAN and SPEC, leaving them uncommitted. Save report artifacts outside the repository. Preserve all unrelated changes.
- Correct stale paths, contradictions, invalid commands and missing details that preserve approved requirements. Do not change requirements, architecture, user-visible behavior, security/privacy boundaries, dependencies, services, cost or delivery scope without approval. Record a recommendation as a pending decision and keep working instead of stopping to ask. If a correction also changes a boundary, it requires approval.
- Do not read secrets, install dependencies, commit, push, open PRs, post comments, merge or deploy during validation. Printing a handoff does not execute it or grant these permissions.
- Research and recommendations grant no permission to download, install, execute or replace dependencies, change manifests/lockfiles, or enable services/plugins. Keep those actions outside validation; record any separately required approval in the handoff. Do not execute the plan's bootstrap, package-manager or plugin commands merely to investigate them.
- **Public research runs by default**: do not ask before each lookup. Read [public research](references/research-permissions.md) before the first lookup. Send only public, non-confidential terms: never private code, plans, paths, personal data or secrets. Record every lookup in the report. If the user declines research or access is unavailable, make no lookup, record the limit and continue independent local checks. Add no telemetry.
- A detached Git worktree isolates working files; it is not a security sandbox. Inspect planned commands before executing them. Do not run commands that touch production, shared databases, external services, credentials, unapproved networks or destructive operations without explicit authorization. Record the blocked check and continue independent work.
- A read-only request overrides document edits and execution: inspect only, report that rehearsal was not run, and do not imply that text review proves runtime behavior.
- Do not stop to ask routine questions. For a reversible clarification inside the approved scope, apply the recommended best practice, continue, and record the choice and reason. Ask only for a missing required path or an ambiguous document pairing. A material scope/security change or permission stays pending without stopping independent work. Silence never supplies required approval.

## Workflow

1. **Establish the baseline.** Read PLAN, SPEC and the relevant code, tests, configuration and locked dependency versions. Record source worktree, branch or detached HEAD, `git status --porcelain -uall`, worktrees, intended base SHA and the exact scope. Distinguish observed HEAD from the intended implementation base. If part of the scope is already implemented, review the remaining tasks and record that choice. If all of it is implemented, stop and report that without a validation verdict.
2. **Preserve original evidence.** Read [references/html-report.md](references/html-report.md). Create its private run directory; copy untouched PLAN and SPEC there before edits. Record document hashes, requirement IDs, phases, unique numbered tasks, implementation/supporting tasks and dependencies/services. Use Unknown for an unrecoverable baseline.
3. **Review coverage and risks.** Map every scoped SPEC requirement to a PLAN task and a meaningful test; map every task back to a requirement. Check current interfaces, exact files, assertions, error paths, sequencing, security/privacy, performance where relevant, and rollout/rollback. Identify proposed/changed dependencies and existing security-critical dependencies relevant to the scoped behavior. Do not audit the entire dependency tree indiscriminately. When applicable, read [dependencies and alternatives](references/dependencies-and-alternatives.md) and compare the original approach with at most two strong alternatives, considering the existing implementation or no new dependency. Verify external claims through recorded public lookups. Label findings Verified, Assumption or Unknown and cite dated primary-source evidence. If no concern or consequential alternative applies, record that briefly; do not invent a comparison or a decision menu.
4. **Revise with scope control.** Repair defects inside existing tasks where practical. Require precise interfaces, fixed values, test assertions and commands; do not demand complete routine implementation bodies. Keep existing document structure and decision IDs. Explain every task split/addition/removal and repeated check. Preserve the branch, review and merge conventions that repository instructions define, or the user's where the repository's are silent; do not invent others. Collect material approval questions; leave affected requirements unchanged until answered.
5. **Rehearse the authorized scope.** Inspect planned commands, wrappers, lifecycle/install scripts, downloads, permissions and external/shared-state effects before running anything. Block only tasks dependent on unresolved safety or permission decisions; continue independent approved checks. Create a new detached worktree at the confirmed implementation base. Use a gitignored `.worktrees/plan-dryrun-<topic>` path or a session temporary directory. Implement enough of each authorized task to exercise its instructions and assertions; skip installation, dependency changes, commit, push, PR and deployment steps. Run only approved focused commands whose dependencies already exist and whose use is authorized; do not execute a suspect dependency to assess its safety. Record exact commands, exit codes, outputs and relevant counts. A blocked environment is a recorded limitation, not a passing check. Repair the plan when an actual mismatch exposes a defect.
6. **Obtain an independent cold read.** This skill explicitly requests one fresh review agent when delegation is available and permitted. Use [references/plan-reviewer.md](references/plan-reviewer.md), original scope snapshots and current documents. Reviewers are read-only and return findings as their final response. Wait for the completed response, verify findings and record their disposition. If an independent reviewer is unavailable, disclose that gap and use Not ready until a separate review is supplied; never present self-review as independent. Recheck material later edits.
7. **Record decisions; do not stop to ask.** Complete independent validation, review and report preparation without pausing for choices. For a routine, in-scope choice, apply the recommended best practice and record the question, choice and reason in `decisions_without_reply`; reflect it in the selected documents where needed so they remain usable. For a choice that needs approval, write a concise menu in section 6: keep the original approach, adopt a named verified alternative (at most two), or defer. Mark the recommendation with reasons, tradeoffs, effort and High/Medium/Low confidence. A blocked option must name its unsatisfied conditions; choosing it does not waive execution approvals. Leave affected requirements unchanged and dependent tasks waiting. The final reply names each pending choice and its recommendation in one line; the user can answer later. When the user answers, record it in sections 5–6, apply and recheck the affected changes, then re-render the report, context and handoff. Once earlier phases have merged, validate the remaining phases as a phase-only validation instead, as the handoff template describes. Treat the earlier handoff as historical. Do not repeat settled questions or convert defaults into user approvals. Recheck affected sections after an approved change without chasing a perfect score.
8. **Clean up and deliver.** Inspect the exact worktree created by this run, preserve evidence, then remove only that disposable worktree. Force removal is allowed only for its known rehearsal edits; never remove another checkout or unknown work. Compare final branch, status and worktree inventory with the baseline. Report concurrent changes without reverting or switching them. Score and render the complete report below.

## Report and handoff

Read [references/report-contract.md](references/report-contract.md) for the rubric and eight required sections. Deliver both five-dimension comparison tables and their calculated averages, decision confidence with evidence, scope comparison, actual checks and limits, and the complete handoff. Include applicable dependency/alternative comparisons inside this report. Dependency decisions use High/Medium/Low with reasons and unknowns, never numeric trust scores. Existing document scores and subjective readiness estimates are not security guarantees or calibrated probabilities.

For new reports, use format version 3: a “Feature at a glance” diagram with 3–7 plain-language blocks above the eight evidence sections, concise summaries with expandable technical details, “Decisions made without your reply” at the end, and the phase grouping below. Keep blockers, pending approvals and both full score tables visible. Target 50–80 words per launch prompt, referencing the plan, spec and saved report; do not duplicate the evidence in it. Existing reports and plans are not migrated or reformatted merely because the plugin changed.

- **Ready:** no material blocker or unresolved approval for the named implementation scope, with the independent review completed.
- **Ready after approvals:** only identified non-blocking approvals remain; dependent work waits.
- **Not ready:** a blocker remains or required independent review/evidence is missing. Include a remediation prompt stating `Do not start dependent implementation.`

### Phase grouping

Group the validated tasks into implementation phases so that each phase runs in its own fresh session. The grouping lives only in the report and `context.json` (`task_inventory` and `phases`); never add, rename or reorder phase headings or tasks in the plan file for it.

- Put every validated task in exactly one phase, in plan order. Never split or move a task.
- Never cross a phase or part the plan already defines. Split a plan phase larger than about 5 tasks into consecutive sub-phases; keep small plan phases as they are, even with one task. A plan with no phases of its own and 5 or fewer tasks is one phase.
- Each later phase's prompt confirms the previous phase is merged; never weaken that check. A delivery that cannot merge each phase on its own is a plan defect: apply per-phase delivery from repository or user instructions, otherwise raise it as an approval in section 6.
- Target 3–5 tasks per phase. End each phase where the tests pass and its PR can be reviewed on its own.
- Record for each phase whether it is docs-only, whether it needs a security review and why (auth, user input, secrets, dependencies, CI workflows), and whether it is ready or waits, naming what it waits for.
- Phases run in order, so a waiting phase holds back every later phase. A phase whose tasks are only partly approved waits as a whole. If the first phase waits, no phase can start: section 8 holds one prompt that names what to resolve and says `Do not start dependent implementation.`
- A phase-only validation groups only the selected scope.

Suggest, never set, a reasoning effort for the next session, as described in the template. Instantiate [handoff-template.md](handoff-template.md) with verified paths: one prompt per ready phase, each naming its phase and tasks and stopping at that phase's end. Keep revisions, checks, decisions and permissions in the referenced report/context. Never add commit, PR, comment, merge, deployment, dependency or service permissions. Repository-specific workflow belongs in repository instructions, not in the universal launch prompt. The recommended per-phase workflow for repositories is published at https://snowholt-labs.github.io/plan-validation/phased-implementation/.

Use `scripts/render_report.py` with the files described in [references/html-report.md](references/html-report.md). Inspect the output, the exact `handoff.txt` and each `handoff-phase-<id>.txt` listed under `phase_handoffs` in the renderer's JSON output. The renderer checks structure, arithmetic and document fingerprints; it does not prove that an agent review or command actually occurred.

Return a brief verdict, a clickable absolute link to `report.html`, the suggested effort for the next session, and any immediate blocker or pending choice. Render new reports with `--open`, and say the report was sent to the browser only when the renderer printed `"opened": true`. If routine defaults were used, briefly identify the choices and reasons at the end; the report retains the complete record. The HTML must contain the full report even when chat is concise. If the user asks for the full report in chat, include all eight sections, the feature overview and defaulted decisions as well.

## Resume or repeat

Keep the original/revised snapshots, hashes, commands/results, reviewer response, tested SHA, scope, approvals, report and handoff in the durable run directory. Read that record after compaction; never reconstruct counts or approvals from a vague recap.

When asked to repeat results, verify current document hashes, worktree, base and approvals, then link the saved complete report. Regenerate missing HTML from saved evidence without claiming a new validation; pass `--open` on a re-render only when the user asked to see the report again. Mark changed or unverifiable state historical; retain the historical prompt and provide a current remediation prompt when needed. Do not replace recorded hashes to make stale evidence appear current. Static HTML only reflects checks made when rendered.
