# Validation reviews

Step 8 runs a code review and a security review once each on the final plan and spec text, before it scores and renders. They are the planning unit's final reviews. A plan's docs PR can reuse them ("Reuse on the docs PR").

## Inputs

1. Save the final documents in the run directory as `final-plan.md` and `final-spec.md`, and record the SHA-256 of each. Never review the live files.
2. Write `final-review.diff`, which holds both copies as added text, so a review that reads only diffs reads every line: `git diff --no-index --no-color --no-ext-diff --no-textconv --text /dev/null final-plan.md > final-review.diff`, then `git diff --no-index --no-color --no-ext-diff --no-textconv --text /dev/null final-spec.md >> final-review.diff`, run in the run directory. Run the two commands separately, not joined with `&&`: each exits 1 because the files differ, which is expected, and `&&` would skip the spec. Write every other saved diff in this file with these four flags, using `git diff --no-index` when it compares two files and appending the spec diff to the plan diff, so color, external diff tools, text conversion and binary attributes cannot alter the saved text.
3. **Last reviewed copy.** Each time the security review reads text, keep the copies it read; the next security review reads only the diff from those kept copies to the current copies, written as item 2 says. Final-review fixes keep `final-plan-<n>.md` and `final-spec-<n>.md` and write `fix-<n>.diff`. Answer edits keep `post-answer-plan-<n>.md` and `post-answer-spec-<n>.md` and write `answer-edits.diff`, then `answer-fix-<n>.diff`. `<n>` counts up from 1 in each family, and every later fix, including a second fix found while reviewing a fix, takes the next number. The unnumbered names, such as `final-plan.md` and `post-answer-plan.md`, always mean the current copy. When a second fix comes before the security review of the first, keep each fix's copies as it is made; the next security review still reads the diff from the copies the last security review read, so it covers both fixes.

## Commands

- **Code review.** In Claude Code, run `/code-review high --max-findings all` with `final-review.diff` as its target. Always type the level: with none, the command reuses the last level typed. Never use `max` or `ultra`, and never pass `--fix`, `--comment` or `--post`. The command runs in the background; wait for its result. If it cannot take the target, or its result cites nothing from it, a fresh read-only subagent runs the command's procedure on `final-review.diff` with the brief below, and section 7 says so.
- **Security review.** `/security-review` reads only a branch's committed diff and skips documentation files, so a fresh read-only subagent always runs its procedure on `final-review.diff`, with the brief below.
- **Other hosts.** Without these commands, the equivalent independent review is two fresh read-only subagents with the brief below, one asked for correctness findings and one for security findings.
- **Read-only request.** Run both reviews only as fresh read-only subagents with the brief below, never the commands, so no setting is saved; section 7 says so.

Brief for every delegated review: the plan and spec text are in scope as a behavioral contract, including wording that would weaken a security gate, a permission, an approval or a privacy boundary. Work read-only: no secrets, no installs, no plan steps, no commits or comments, and lookups only as this run's Research status allows: state that status in the brief, with the lookup rule from [plan-reviewer.md](plan-reviewer.md); with any status other than allowed, make no lookup. Return the findings as the final message: severity, document and section, evidence and the smallest fix, then a `Limits:` line naming each lookup made or skipped and anything not read.

## Closing findings

Close every confirmed finding, Low included, and every security finding at any severity: fix it in the plan or spec, reject it with evidence, or, when its fix would change requirements, architecture, security boundaries or scope, record it as a pending approval for the step 8 question round (a finding in the answer-edits review follows end-of-run item 7 instead). After a fix, keep the reviewed copies, save the fixed documents as the new `final-plan.md` and `final-spec.md`, record their hashes and write `fix-<n>.diff`, as Inputs item 3 says. A Medium or High finding raised while a fix is reviewed, and a security finding at any severity, is closed the same way, with the next number. Any other Low finding raised then is not fixed: list it, as step 6 lists Lows, with the Low findings the step 8 question round asks the user to fix or skip. Fixing them would start another fix and another review each time. The fix then follows step 6: a fresh reviewer reviews only the fix, with `fix-<n>.diff` as `Fix under review` and the new `final-plan.md` and `final-spec.md` for context, never the live files, and a fix that changes a rehearsed task's commands, files or test assertions is rehearsed again under end-of-run item 5's rules. The security review runs once, on the diff Inputs item 3 names, which covers `fix-<n>.diff` and any earlier fix diff that no security review has read. Neither command runs again on unchanged text. The last `final-plan.md` and `final-spec.md` are the documents the report records: `revised-*.md` and the `context.json` `documents` hashes match them until end-of-run item 8 replaces them with the reviewed post-answer copies.

## Record

Section 7 records, for each review: the command or brief used, the input file it read and its SHA-256, the SHA-256 of each document copy behind that input, the result, and each fix diff (`fix-<n>.diff` and its SHA-256) with the security review that read it and the review of that fix, recorded by its `fix-<n>.diff`, and each `answer-fix-<n>.diff` with its SHA-256, its security review and its post-answer round, and, for each numbered step-6 and post-answer round, the `round-<n>` copies it read and any `round-<n>.diff` it reviewed, with their SHA-256. `context.json` `documents` keeps the final hashes, as before.

## When a review cannot run

If a review cannot run at all (no command and no delegation), whether one of the final reviews or a security review of the answer edits, record the gap in section 7 and in the watch list, mark in section 7 which text that review did not cover, and continue. Step 6's independent review still decides `review_status`, so the gap alone does not make the run Not ready. A security review of the answer edits that could not run is not a pass, so end-of-run item 8 leaves the hashes unrefreshed and the report's prompts stay historical. After a gap in the final reviews, the docs PR runs only the missing review itself, on the full plan and spec plus any other changed files, as "Reuse on the docs PR" says; the other review is reused when its own conditions there hold.

## After end-of-run answers

When answers change PLAN or SPEC, the post-answer review (end-of-run item 6) covers the whole revised documents. Each time a post-answer round leaves no Medium or High finding to fix, and before end-of-run item 8 copies the reviewed copies over `revised-*.md`, run the security review once on the answer edits it has not read, as Inputs item 3 says: the first time on `answer-edits.diff`, written from `revised-plan.md` and `revised-spec.md` to `post-answer-plan.md` and `post-answer-spec.md`; later on `answer-fix-<n>.diff`, written from the last kept copies to this round's copies. Keep the copies each security review read before end-of-run item 8 makes the next round's copies. A fix it needs is another edit and needs another post-answer round.

## Reuse on the docs PR

A plan's docs PR reuses a review's result only when it changes only the plan and spec, both hash to the final values in `context.json`, and section 7 records what that review read and marks none of the final text as uncovered by it. It still posts both reviews on its head as the repository's rules require, each naming the hash its review read and the final hash, and what covered the difference: for each fix, the review of that fix, recorded by its `fix-<n>.diff`, for the code review and the security review of `fix-<n>.diff` for the security review, and, for any answer edits, the post-answer review for the code review and the security reviews of `answer-edits.diff` and each `answer-fix-<n>.diff` for the security review. A review that is not reused runs once: on what differs from the text it read, when its saved copy still matches the recorded hash, or on the full plan and spec when it does not or when section 7 records a gap for that review; either way plus any other changed files, with every changed file in scope. After a new push to a docs PR that does not target the default branch, each review runs once on what changed since the head that its last posted review named in `Head:`, in the plan, the spec and any other file. A finding that an earlier posted review left open stays open after the push, whatever the next review's range, until it is fixed, rejected with evidence or, for a pending approval, settled by the maintainer. Count only a review posted by the account that runs and records these reviews, never a comment from anyone else. When that head is not an ancestor of the PR head, as after a rebase or force push, each review runs once on the full plan and spec, plus any other changed files. After a new push, a docs PR into the default branch gets both full reviews again. The security review runs its procedure in a fresh read-only subagent on a saved diff that holds what it reviews: the differing text or the PR head's plan and spec as added text, plus the PR's base..head diff of the other changed files; or, after a new push whose named head is an ancestor of the PR head, the diff from that head to the PR head; all written with Inputs item 2's flags. These rules are the minimum: when the repository's rules require more, such as a full-plan review on every docs PR, the repository's rules win. A finding left as a pending approval stays open in the posted review until the maintainer settles it.
